## 2. 데이터로 만들어지는 것

### 2-1. 매출관리 화면에서 나오는 것

**대시보드 메인** (`/dashboard`):
- 이번달 총 매출
- 전달 대비 증감율 (▲/▼ + %)
- 전년 동월 대비 증감율
- 거래 건수
- 일 평균 매출
- 일별 매출 막대 차트 (Recharts)

**매출 관리 페이지** (`/dashboard/sales`):
- 일별 매출 입력 폼 (날짜/금액/카테고리/시간대/메모)
- 매출 내역 목록 (최근 50건, 수정/삭제 가능)
- 전체 합계 표시

**카테고리/시간대 분류**:
| 분류 | 항목 |
|---|---|
| 카테고리 | 음료 / 디저트 / 기타 |
| 시간대 | 오전 / 오후 / 저녁 |

### 2-2. AI 인사이트 화면에서 나오는 것

**인사이트 페이지** (`/dashboard/insights`):

1. **4개 매출 요약 카드**: 이번달 / 전달 대비 / 전년 동월 대비 / 일 평균
2. **Claude AI 분석 텍스트**: 원인 분석 + 추천 액션 2~3가지
3. **카테고리별 매출 프로그레스 바**: 음료/디저트/기타 비율
4. **시간대별 매출 프로그레스 바**: 오전/오후/저녁 비율
5. **"마포구 실데이터 반영" 배지**: RAG 검색 성공 시 표시

**AI가 분석에 참고하는 것**:
- 사용자의 이번달 매출 데이터 (my 카페)
- 마포구 동일 상권 카페 평균 통계 (RAG)
- 매출 변화율에 따른 동적 전략 쿼리

**매출 변화에 따른 동적 RAG 쿼리**:

| 상황 | 검색 쿼리 |
|---|---|
| 매출 하락 (≤ -10%) | "카페 매출 하락 원인 회복 전략", "마포구 카페 비수기 대응" |
| 매출 상승 (≥ +10%) | "카페 매출 상승 유지 전략", "마포구 카페 성수기 매출 확대" |
| 안정 | "마포구 카페 매출 안정 유지 전략" |
| 기본 | "마포구 카페 {월}월 매출 계절 패턴" |

> ⚠️ **한계**: 현재 RAG에는 전략 가이드 문서가 없고 숫자 통계만 있음. Claude가 통계를 해석해 전략을 생성하는 구조.

### 2-3. Proactive 트리거 (자동 알림)

인사이트 분석 시 매출 변화가 감지되면 `trigger_log` 테이블에 자동 기록:

**상승 감지 메시지**:
```
[매출 상승 감지] 2026년 4월 매출이 전달 대비 11.4% 증가했습니다.
AI 인사이트에서 상승 원인과 유지 전략을 확인해보세요.
```

**하락 감지 메시지**:
```
[매출 하락 감지] 2026년 4월 매출이 전달 대비 8.3% 하락했습니다.
AI 인사이트에서 원인 분석과 회복 전략을 확인해보세요.
```

## 4. 데이터 흐름

```
[사용자]
    │
    ├── 매출 수동 입력
    │      └── sales 테이블 (Supabase)
    │              └── user_id, date, amount, category, time_slot, memo
    │
    └── AI 분석 요청
           │
           ├── sales 테이블에서 매출 집계
           │       └── 현월 / 전달 / 전년 동월 조회
           │
           ├── documents 테이블에서 RAG 검색
           │       └── mapo_stats 카테고리 (마포구 카페 통계)
           │               └── BGE-M3 임베딩 → 코사인 유사도 검색
           │
           ├── Claude Sonnet 4.6 API 호출
           │       └── 매출 데이터 + RAG 컨텍스트 → 인사이트 생성
           │
           └── trigger_log 테이블 자동 기록 (Proactive)
```

## 5. DB 테이블 구조

### sales 테이블

```sql
id          UUID  PK
user_id     UUID  → users(id)
date        DATE
amount      INT   -- 원 단위
category    TEXT  -- '음료' | '디저트' | '기타'
time_slot   TEXT  -- '오전' | '오후' | '저녁'
memo        TEXT  (선택)
created_at  TIMESTAMPTZ
```

### documents 테이블 (RAG)

```sql
id              BIGSERIAL PK
category        TEXT  -- 'mapo_stats' | 'regulation' | ...
source          TEXT  -- API 출처 + 분기 정보
chunk_index     INT
content         TEXT  -- 임베딩된 텍스트 청크
embedding       VECTOR(1024)  -- BGE-M3
metadata        JSONB -- {area, induty, quarter, data_type}
created_at      TIMESTAMPTZ
```

## 7. 부족한 부분 (개선 필요)

### 🔴 기능적 한계

| 항목 | 현재 | 필요한 것 |
|---|---|---|
| 매출 수집 방식 | 수동 입력만 | POS 연동, 배달앱 연동, 카드 매출 자동 연동 |

## 9. 전체 개선 실행 계획 (최대 정확도·최대 데이터 목표)

> 기능적 한계 + 데이터 부족을 모두 해소하기 위한 단계별 실행 순서.
> 앞 단계의 데이터가 뒷 단계의 분석 품질을 높이므로 순서를 지켜 진행.

---

### Phase 1 — 데이터 수집 기반 구축 (먼저 진행해야 이후 분석이 의미 있음)

#### Step 1. 2024년 최신 분기 데이터 수집

**목표**: 현재 최신 분기(2023Q4)를 2024년 전체로 확장

**작업 파일**: `backend/data/crawlers/` 하위 골목상권 크롤러

**방법**:
1. 기존 크롤러에서 `quarters` 리스트에 2024년 분기 파라미터 추가
   ```python
   quarters += ["20241", "20242", "20243", "20244"]
   ```
2. `VwsmTrdarSelngQq`(추정매출), `VwsmTrdarStorQq`(점포현황) 두 API 모두 재실행
3. `backend/scripts/` 하위 시드 스크립트 실행 → Supabase `documents` 테이블 갱신
4. 수집 전 서울 열린데이터광장에서 2024년 분기 데이터 제공 여부 확인 필요

**검증**: Supabase에서 `select count(*) from documents where category='mapo_stats' and metadata->>'quarter' like '2024%'` 로 확인

---

#### Step 2. 상권변화지표 수집 (`VwsmTrdarlxQq`) — CSV 우회 방식

**목표**: API 500 오류로 미수집된 HH/HL/LH/LL 상권 등급 데이터 확보

**방법**:
1. 서울 열린데이터광장 골목상권 분석 페이지에서 CSV 파일 직접 다운로드
   - 대상: `상권변화지표` 데이터셋 (연도별 파일)
2. `backend/data/parsers/` 에 CSV 파서 추가
   ```python
   # 파싱 대상 컬럼: 기준_년_코드, 기준_분기_코드, 상권_코드, 상권_코드_명,
   #                상권_변화_지표_명 (HH/HL/LH/LL), 운영_영업_개월_평균
   ```
3. 파싱 결과를 `documents` 테이블에 `category='mapo_commercial_change'` 로 삽입
4. `metadata` 예시: `{"area": "홍대입구", "quarter": "20231", "grade": "HH", "meaning": "상권확장"}`

**HH/HL/LH/LL 의미**:
| 코드 | 의미 |
|---|---|
| HH | 매출·유동인구 모두 높음 (핵심 상권) |
| HL | 매출 높음, 유동인구 낮음 (목적형 상권) |
| LH | 매출 낮음, 유동인구 높음 (경쟁 과열) |
| LL | 매출·유동인구 모두 낮음 (침체 상권) |

#### Step 3. 유동인구 데이터 수집 (`VwsmAdstrdFlpopW`)

**목표**: 시간대별·요일별 유동인구 수 확보 → "이 시간대 유동인구 많음" 분석 가능

**API 정보**:
```

파라미터: STDR_YYQU_CD(분기), ADSTRD_CD(행정동코드)

  - 시간대_00~06_유동인구_수 ~ 시간대_21~24_유동인구_수 (6개 시간대)
  - 요일별_유동인구_수 (월~일)
  - 남성_유동인구_수, 여성_유동인구_수
```

**작업 순서**:
1. `backend/data/crawlers/` 에 `mapo_population_crawler.py` 신규 작성
2. 마포구 9개 상권의 행정동 코드 매핑 테이블 작성 (`backend/core/constants.py` 에 추가)
3. 2021Q4 ~ 2024Q4 전 분기 수집
4. `documents` 테이블에 `category='mapo_population'` 으로 삽입

#### Step 5. 날씨 데이터 수집

**목표**: "비 오는 날 매출 패턴" 분석 → 날씨-매출 상관관계 도출

**API 정보**:
```
제공: 기상청 (공공데이터포털)
엔드포인트: https://apis.data.go.kr/1360000/AsosDalyInfoService/getWthrDataList
파라미터: startDt, endDt, dataCd=ASOS, dateCd=DAY, stnIds=108 (서울 관측소)
주요 반환 필드: 평균기온(avgTa), 강수량(sumRn), 최대풍속(maxWs), 평균습도(avgRhm)
비용: 무료 (하루 10,000 콜 제한)
```

**DB 설계 — `weather_data` 테이블 신규 추가**:
```sql
CREATE TABLE weather_data (
  id         BIGSERIAL PRIMARY KEY,
  date       DATE UNIQUE,
  avg_temp   NUMERIC(4,1),   -- 평균기온 (℃)
  rain_mm    NUMERIC(6,1),   -- 강수량 (mm), 0이면 맑음
  is_rainy   BOOLEAN,        -- 강수량 > 0
  max_wind   NUMERIC(4,1),   -- 최대풍속 (m/s)
  avg_humid  NUMERIC(5,1),   -- 평균습도 (%)
  created_at TIMESTAMPTZ DEFAULT now()
);
```

**작업 순서**:
1. 공공데이터포털 기상청 API 키 발급
2. 과거 날씨 일괄 수집 (2021-01-01 ~ 현재) → `weather_data` 테이블 삽입
3. APScheduler로 매일 전날 날씨 자동 수집 (일 1회)
4. 인사이트 분석 API에서 날씨 데이터 조인
   ```python
   # 매출 데이터 조회 시 날씨 정보 병합
   # "비 오는 날 평균 매출: X원 / 맑은 날 평균 매출: Y원" 형태로 Claude에 전달
   ```
